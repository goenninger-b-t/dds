# WP-SHMEM — SHMEM vs UDP-loopback latency/throughput (NFR-PERF-6, FR-LANG-7)

Task F3 of WP-SHMEM: quantify the shared-memory intra-host data plane (FR-XPORT-2) against the UDP-loopback
baseline. Per the operating contract, no hot-path change lands without a before/after measurement — this is
that measurement. Generated by `dds.bench:run-bench-shmem` (entry: `make bench-shmem`).

## Method

Both bench nodes run in ONE process, so they share a `host-uuid` (MD5 of the hostname); with
`*shmem-enabled*` T and a SHMEM receive segment created on each node, the user-DATA push auto-routes over
shared memory (`%shmem-dest` matches the same host-uuid + the peer's advertised SHMEM locator). The UDP
baseline rebinds `*shmem-enabled*` NIL around node creation to force the all-UDP loopback path. **Every SHMEM
run asserts `disc-node-shmem-sends` advanced past 0** — so the SHMEM columns are PROVEN to have traversed
shared memory, not a silent UDP fallback (the run errors otherwise). Latency is one-way (RTT/2, single
in-flight PING/PONG); the clock is `dds.pal:monotonic-ns` (~microsecond resolution via the PAL real-time
clock). `bytes/sample` is the `dds.pal:bytes-consed` delta over the measured loop (whole path, all threads;
SBCL-exact, Clasp reports 0 — a documented NFR-PORT gap).

## Interpretation (honest — FR-LANG-7: measure, don't assume)

**Latency: SHMEM wins.** SHMEM cuts the one-way median (p50) latency from ~20000-29500 ns (UDP loopback) to
~13000-20000 ns — a **1.2x-1.85x speedup**, largest for the smallest 16 B payload (1.85x). SHMEM's p99 is
comparable-to-better than UDP's at every size except the noisy 64 B point. This is the expected single-in-flight
win: for one outstanding message the pshared mutex is uncontended and a userspace condvar wakeup beats the
full UDP loopback socket round-trip (two trips through the kernel networking stack).

**Throughput: UDP loopback WINS decisively — SHMEM is the LOSER here.** At batch=1 SHMEM delivers only
**0.05x-0.38x** of UDP's send rate (i.e. UDP is 3x-20x FASTER). The cause is structural: `%shmem-send`
takes a pshared mutex, signals a condvar, and unlocks the destination's notify block on EVERY message
(shmem.lisp `%shmem-send`), and on macOS the kernel's loopback path is so heavily optimized that this
per-message lock+signal is pure overhead in a tight blast. Batching (batch=100) narrows the gap to 0.36x but
still does not beat UDP — coalescing amortizes the per-datagram framing but the per-flushed-datagram SHMEM
lock+signal remains. **This is a legitimate, important finding:** the current single-mutex/condvar SHMEM
notification is a throughput bottleneck, and it directly justifies the planned lock-free-MPSC follow-up — a
per-lane lock-free ring with a batched/coalesced wakeup (signal once per drained burst, not once per message)
is what a throughput win would require.

**Latency `max` tail.** Both transports show large, rare max outliers (UDP up to ~5.8 ms, SHMEM up to ~0.75 ms)
that are scheduler/wakeup jitter on a shared 10-core machine (and the occasional GC pause coinciding with a
futex wakeup), NOT a steady-state cost — p50 and p99 are the meaningful figures. Notably SHMEM's max tail
(~0.5-0.75 ms) is consistently *lower* than UDP's worst (~5.8 ms at 16 B), so SHMEM is also less prone to the
worst-case loopback-scheduling spike.

**Allocation (NFR-PERF-8) — NOT 0-alloc on EITHER transport, by design.** `SHM b/samp` is ~10138-12156
bytes/sample. The matching UDP baseline is ~9334 bytes/sample (measured separately with the same harness), so
SHMEM adds only ~800-2000 bytes/sample over UDP — the per-push `make-shmem-locator` struct plus a `subseq` of
the remote prefix in `%group-shmem-dest`/`%shmem-dest`. Critically, **the ~9-12 KB/sample is the documented v1
disc-layer data-plane allocation** (per-sample heap copies; `dataplane.lisp` is explicitly NOT the gated
hot path — "the gated hot-path files are untouched"). The NFR-PERF-8 0-alloc gate (`make mem`) applies to the
XCDR codec, which is already 0-alloc; this harness exercises the un-optimized v1 dataplane above it. So the
honest statement is: **SHMEM did not regress allocation meaningfully, but neither transport is 0-alloc in this
v1 path** — driving this dataplane toward 0-alloc is separate follow-up work, independent of the transport.

**Note on throughput variance.** The throughput rows are noisy run-to-run (the 64 B / batch=1 UDP figure
varied ~7k-67k samples/s across runs): `delivered-samples-per-s` includes the 5 ms receiver poll granularity
and the reliable HEARTBEAT/ACKNACK handshake, and macOS scheduling on a shared box adds jitter. The
*direction* of the result is stable and reproducible (SHMEM batch=1 throughput is always a fraction of UDP);
the absolute samples/s should be read as order-of-magnitude, not precise.

## Bottom line (initial, pre-optimization — HEAD 36562ed)

SHMEM is a clear **latency** win (up to 1.85x lower one-way median for small samples) and a clear **throughput**
loss at the current per-message-signal design (3x-20x slower than the heavily-optimized macOS UDP loopback).
The SHMEM path is proven live (shmem-sends asserted > 0 on every SHMEM run). The throughput result is the
quantified motivation for the dest-cache + conditional-wakeup work below (and the still-pending lock-free-MPSC follow-up).

# After: dest-cache + conditional wakeup (FR-XPORT-2, FR-LANG-7)

Two optimizations landed on `wp-shmem` after the initial measurement above, each justified by the profile:

- **(A) cache the resolved SHMEM destination per remote.** The pre-A send resolved a remote's `shmem-locator`
  on EVERY datagram — a node-lock + `gethash` in `discovered` + a `subseq` of the prefix + a fresh
  `make-shmem-locator` allocation per send (`%shmem-dest`). It is now memoized per remote prefix
  (`disc-node-shmem-dest-cache`, sentinel `:none` for a non-SHMEM peer), filled once under the node lock and
  reused on every subsequent send, invalidated on the peer's SPDP re-discovery (`%record-participant`) and on
  its lease-out (`%lease-sweep`). Steady-state send now does one cheap `gethash` and **zero** per-datagram
  `make-shmem-locator` allocation.
- **(B) conditional (parked-flag) wakeup.** The pre-B send did `pshared-lock` + `pshared-cond-signal` +
  `pshared-unlock` (a futex syscall) on EVERY send, even into a busy receiver. A `parked` u64 (offset 200, in
  the existing [192,256) notify region) is now set/cleared strictly under the pshared mutex around the
  receiver's `cond-wait`; the sender (`%shmem-send`) issues a FULL fence then reads `parked` and signals ONLY
  when `parked = 1`. The receiver publishes `parked = 1`, FULL-fences, and RE-CHECKS the data predicate before
  actually waiting (the Dekker StoreLoad handshake), so a skipped signal is provably never a lost wakeup. A
  busy (draining) receiver is never futex-woken — the wasted wake the initial report identified is eliminated.

## Honest read of the throughput result (FR-LANG-7)

**The `samples/s` throughput rows do NOT show A+B's benefit, and that is a property of the HARNESS, not of the
optimizations.** `send-samples-per-s` is wall-clock from the first publish to `flush-batch` return over the
RELIABLE data plane, so it is dominated by the HEARTBEAT/ACKNACK handshake and the 5 ms receiver-poll
granularity — not by the per-message send cost. The proof it cannot resolve the per-send cost: the UDP
*baseline* swung ~10x run-to-run between the two reports (256 B / batch 1: 53091 → 5220 samples/s) with no UDP
code change. Both transports are gated by the same reliable-handshake overhead in this harness, so the spr
ratio (~0.35x-0.39x here) is noise around the reliable round-trip, not a measure of the SHMEM notify path.
The 256 B / 1024 B batch-1 cases are no longer the 0.05x-0.06x outliers the initial report saw (they sit with
the rest at ~0.36x-0.39x), but the harness is too coarse to claim that as A+B's doing.

**To isolate A+B's effect, a direct send-path micro-bench** (one sender, one receiver thread, the same SHMEM
ring + drain, NO reliable handshake) compares the landed conditional-wakeup send against a forced-unconditional
(pre-B) send over 500 000 small records, all delivered (correctness preserved):

| send path | records/s (3 runs) | delivered |
|-----------|--------------------|-----------|
| conditional wakeup (LANDED, A+B) | 8.05M / 6.61M / 7.22M | 500000 / 500000 / 500000 |
| unconditional signal (pre-B)     | 4.45M / 4.18M / 5.12M | 500000 / 500000 / 500000 |
| **speedup**                      | **1.81x / 1.58x / 1.41x** | — |

So Optimization B is a **~1.4x-1.8x raw-send-throughput win** when the receiver keeps up (it skips the futex
syscall on the common busy-receiver path), with no record loss. Optimization A removes the per-datagram
allocation (≈1 KB/sample, table above). The conditional skip is exercised live by the new `shmem-stress` test
(4 senders × 5000 distinct records → exactly 20 000 delivered, no loss, no hang) and the deterministic
single-threaded reachability check (parked=0 → no wake; parked=1 → signal branch).

## Residual (still open)

The end-to-end *reliable* throughput over the disc data plane remains gated by the HEARTBEAT/ACKNACK handshake
and the receiver-poll granularity, NOT by the SHMEM transport — so the headline `samples/s` is unchanged. The
remaining transport-level item is the planned **lock-free-MPSC** ring (per-lane lock-free enqueue) to drop the
mutex-guarded lane claim; combined with A+B's allocation + futex savings it is the path to a SHMEM throughput
that also beats UDP loopback on the raw send path under heavy contention. The disc-layer reliable-handshake and
poll-granularity costs are a separate (engine/DCPS) follow-up, independent of the transport.

## Bottom line (after A+B)

SHMEM keeps its **latency** win (1.35x-1.94x lower one-way median). Optimization A removes the per-datagram
allocation (SHMEM bytes/sample now at the UDP baseline). Optimization B roughly **1.4x-1.8x**'s the raw SHMEM
send throughput (futex skipped on the busy-receiver path) with provably no lost wakeup — though the coarse,
reliable-handshake-bound `samples/s` harness metric does not surface it. The SHMEM path remains proven live
(shmem-sends asserted > 0 on every SHMEM run). The lock-free-MPSC ring is the remaining transport follow-up.
