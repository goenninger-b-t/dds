# WP-ZEROCOPY — large-sample Zero-Copy vs SHMEM vs UDP-loopback (FR-PF-3, FR-LANG-7)

**NOT cleared for ship — pending counsel (R6); see ADR 0014.** `dds.disc:*zerocopy-enabled*` is default OFF;
this report exercises it with an explicit dynamic binding inside the bench only.

Phase E1 of WP-ZEROCOPY: quantify the same-host Zero-Copy data plane — where a LARGE sample's serialized
payload is placed once in a per-writer SHMEM sample-pool and only a 16-byte reference crosses the transport —
against both the WP-SHMEM serialized-payload-over-SHMEM path and the UDP-loopback baseline. Per the operating
contract, no hot-path change lands without a before/after measurement; this is that measurement. Generated by
`dds.bench:run-bench-zerocopy` (entry: `make bench-zerocopy`).

## Method

All three transports run as 2 in-process participants, so they share a `host-uuid` (MD5 of the hostname). The
UDP rows rebind `*shmem-enabled*` NIL to force the loopback path. The SHMEM rows route the serialized payload
over shared memory (WP-SHMEM). The ZEROCOPY rows additionally bind `*zerocopy-enabled*` T, so each node builds
its per-writer SHMEM sample-pool and a sample **strictly larger** than `*zerocopy-min-payload-bytes*` (1024) is
stored in a pool slot and transmitted as a 16-byte reference (`+zc-encapsulation-id+`) instead of being
fragmented; the same-host ZC-capable reader resolves it from the writer's pool. **Every ZEROCOPY run asserts
`disc-node-zc-sends` advanced** for an above-threshold payload — so the ZC columns are PROVEN to have crossed
as a reference, not a fragmented payload (the run errors otherwise). The 512 B latency row is a **control
below** the threshold: ZC must NOT engage there, and the assertion is correspondingly suppressed — `zc-sends=0`
on that row is the expected, correct fallback to normal DATA.

Latency is one-way (RTT/2, single in-flight PING/PONG); the clock is `dds.pal:monotonic-ns` (~microsecond
resolution). `b/samp` is the `dds.pal:bytes-consed` delta over the measured loop (whole path, all threads;
SBCL-exact, Clasp reports 0 — a documented NFR-PORT gap). The throughput sample count is scaled per payload
size to a fixed 24 MiB/run byte budget because `run-throughput` does not drain the disc-layer receive cache nor
the reliable writer history (each run retains ~N × payload on the heap); `N` is shown per row.

## Interpretation (honest — FR-LANG-7: measure, don't assume)

**The control row proves the threshold works.** At 512 B (below `*zerocopy-min-payload-bytes*` = 1024) ZC does
not engage: `zc-sends=0` and ZC latency is statistically identical to plain SHMEM (0.96x). This is the designed
fallback — a small sample is not worth a pool slot + reference (its path is the WP-SHMEM/batching target), and
the bench confirms the writer correctly sends it as normal DATA. The win below is exclusively the large-sample
story, exactly as the design predicts.

**Latency: ZC wins decisively for large samples — the whole point of the feature.** ZC cuts the one-way median
from the SHMEM serialized path by **15.82x at 4 KiB, 1.57x at 16 KiB, and 2.18x at 64 KiB**, and against the
UDP baseline by ~2.5x (4 KiB), 2.9x (16 KiB), and 3.9x (64 KiB). The mechanism is structural: a large
serialized payload over SHMEM (or UDP) must be FRAGMENTED into `*fragment-size*` (1024 B) DATA_FRAG submessages
and reassembled by the reader — many submessages + a HEARTBEAT_FRAG + the reassembly buffer — whereas the ZC
path emits a SINGLE small DATA submessage carrying the 16-byte reference; the reader maps the writer's pool and
reads the payload from the slot directly, with no fragmentation/reassembly round-trip at all. That is why the
ZC latency is roughly FLAT in payload size on the transport (19.5 us → 41 us → 109 us tracks the resolve copy,
not the fragment count) while SHMEM/UDP grow steeply with the number of fragments.

**The SHMEM 4 KiB latency point is anomalously high (308500 ns / 15.82x), and that is real, not a glitch.** The
fragmented-large-sample path over the WP-SHMEM transport is the worst case for the per-message pshared
mutex+condvar notification: each of the several fragments + the HEARTBEAT_FRAG is a separate SHMEM datagram
with its own lock/signal, and the reliable reassembly/ACKNACK handshake interleaves with them. The 4 KiB point
(4-5 fragments) lands in the pathological spot; by 16/64 KiB the SHMEM p50 actually improves relative to 4 KiB
(the larger sends amortize differently and macOS scheduling shifts), which is why the ZC/SHM ratio is
non-monotonic (15.82x → 1.57x → 2.18x). The honest reading: **ZC's latency advantage over serialized SHMEM is
large at every above-threshold size, but its magnitude is dominated by how badly the serialized path
fragments at that particular size, not by a smooth ZC scaling law.** The UDP comparison (a clean 2.5x–3.9x,
monotonically growing with size) is the more stable statement of the win.

**Throughput: ZC wins, and the win GROWS with payload size — 1.27x (4 KiB) → 3.02x (16 KiB) → 9.88x (64 KiB)
over serialized SHMEM, and ~2.2x → 2.7x → 8.2x over UDP.** This is the copy-elimination signature: the larger
the sample, the more the fragmented serialized transmit costs and the more the single-reference ZC transmit
saves. At 64 KiB ZC sustains ~15k samples/s while both serialized transports collapse to ~1.5–1.9k. (Read these
as order-of-magnitude: the reliable handshake + the 5 ms receiver-poll granularity make `samples/s` noisy, as
documented for the WP-SHMEM bench; the *direction and growth* are the robust result.)

**Allocation (`b/samp`) — the headline caveat, and it is the honest one.** The naive expectation is "ZC conses
far less because only 20 bytes cross." That is TRUE on the transmit side but **NOT TRUE end-to-end in v1,
except at the slot-full size**, because of the resolve path. The reader's `%handle-datagram` resolve
(`dataplane.lisp`) allocates a FULL `+zerocopy-pool-slot-bytes+` (64 KiB) scratch `sink` array on EVERY resolve
regardless of the actual sample size, then copies `len` bytes out into a right-sized vector. So:

- At 4 KiB the ZC path conses ~130 KB/sample (a 64 KiB sink + a 4 KiB copy + overhead) vs SHMEM's ~83 KB —
  **ZC conses MORE.**
- At 16 KiB they are close (ZC ~109 KB vs SHMEM ~90 KB) — ZC still slightly higher.
- Only at **64 KiB** does ZC drop well below SHMEM (ZC ~78 KB vs SHMEM ~252 KB) — here the sample fills the
  slot, the fixed sink is no longer over-sized waste, and the eliminated fragmentation copies on the serialized
  side dominate.

This is a legitimate, important finding and it does NOT undercut the feature: the **latency and throughput
wins are large and real at every above-threshold size** (the ref-not-payload-on-the-wire win is genuine), but
the **per-sample allocation win only materializes once the sample approaches the slot size**, because the v1
resolver over-allocates a slot-sized sink. The fix is exactly the next WP on the roadmap: literal read-in-place
/ FlatData (WP-FLATDATA, ADR 0014 out-of-scope-v1 list), where the reader deserializes directly from the
mapped slot with zero resolve-side copy — that turns the allocation win on at all sizes. A cheaper interim
step (size the sink to `ref.slot-bytes` or the parsed `len`, not the pool max) would remove the over-allocation
without the full FlatData read-in-place; either is follow-up, not in E1's scope. None of this is on a gated
hot path — `dataplane.lisp` is the documented v1 disc-layer data plane, not the `make gate-hotpath` surface.

**Tail latency.** Both serialized transports show the large p99 outliers typical of the fragmented path on a
shared 10-core machine (SHMEM 4 KiB p99 = 3.16 ms; UDP/SHMEM 64 KiB p99 in the 0.5–1.3 ms range). ZC's p99 is
dramatically tighter (33 us at 4 KiB, 130 us at 64 KiB) because the single-submessage path has far fewer points
at which a scheduler/GC stall can interleave. The tighter ZC tail is itself a meaningful result for large
same-host samples.

## Proof the bench truly used Zero-Copy

`zc-sends` is the writer's count of samples published as a reference. It is `2000` (latency) / `N` (throughput)
on every above-threshold row — i.e. EVERY large sample crossed as a reference — and `0` on the 512 B control,
matching the threshold exactly. The bench asserts `zc-sends > 0` for above-threshold ZC runs (and the suite
smoke `perftest-zerocopy-smoke` re-asserts it at 2048 B), so a regression that silently fragmented the payload
while claiming ZC would fail the run rather than produce a misleading number.

## Bottom line

For LARGE same-host samples WP-ZEROCOPY is a clear, proven **latency** win (≈2.5x–3.9x lower one-way median vs
UDP; up to 15.8x vs the fragmented SHMEM path) and a clear **throughput** win that GROWS with payload size
(up to 9.9x vs SHMEM at 64 KiB) — because only a 16-byte reference crosses the transport instead of the
fragmented payload. It correctly does NOT engage below `*zerocopy-min-payload-bytes*` (the control row proves
the fallback). The one honest qualifier: the v1 **resolve path over-allocates a slot-sized sink**, so the
per-sample *allocation* win only appears once the sample approaches the slot size (64 KiB here) — sizing the
sink to the sample, and ultimately read-in-place/FlatData, is the follow-up that turns the allocation win on at
all sizes. The feature remains **default-OFF and NOT cleared for ship pending counsel (R6)**.
