# NFR-MEM allocation ratchet (ADR 0062). One ceiling PER ARCHITECTURE, in bytes/sample.
#
# ⚠️ RE-BASELINED 2026-07-21 — THE NUMBERS BELOW ARE NOT COMPARABLE TO ANY EARLIER ROW.
# mem-per-sample's workload went from 3000 to 60000 samples because the gate had become BLUNTER THAN THE
# WINS IT GUARDS: the measured window carries a FIXED ~65 KB per-run allocation occurring 0-3 times, which
# at 3000 samples lands as a ~22 B/sample quantum — ONE UNCHANGED ARM read 1791 / 1813 / 1835 / 1857, a
# ~65 B spread against a typical slice's ~35 B win. The quantum is per RUN, so it shrinks as 1/samples:
#
#     samples    3000        30000       60000
#     spread     ~65 B       ~3 B        ~0.4 B      (measured, same code, same box, back-to-back)
#
# Across a whole SESSION the 60000 spread is about 3 B (observed 1847.9 / 1850.0 / 1850.9 on identical code),
# and that — not the back-to-back number — is what a ceiling's headroom must cover. arm64's 1880 sits ~29 B
# above the measured 1851, roughly 10x that spread.
#
# The workload is not perfectly scale-free — identical code reads 1857 / 1854 / 1849 at those three counts —
# so the absolute ceiling MOVED with it. That is why arm64 reads ~1849 here while the last 3000-sample row
# said 1813: the allocation did not regress, the instrument changed. Any future change to `samples` is
# likewise a re-baseline of BOTH rows, never a free knob (see mem-per-sample's docstring).
#
# Per-architecture, because SBCL's per-sample allocation differs materially by arch — measured, not assumed:
#   arm64   1847.9-1850.9   (2026-07-21 @60000 samples; ~0.4 B back-to-back, ~3 B across a session. Latest win: the RX STORE-COPY POOL —
#                            the receiver's per-sample copy out of the receive buffer is drawn from an arena
#                            pool and carries its extent in the buffer's capacity, ADR 0078, -33 B and LINEAR
#                            IN PAYLOAD SIZE; prior ADR 0062/0065-0068/0072/0073/0075/0076/0077.
#                            Cumulative from the ADR 0062 baseline of 3560 (measured at 3000): ~-48%.)
#   x86_64  ~1945 (est)     (2026-07-21: NOT measured at 60000 here — the dev box is arm64, CI is x86_64-only.
#                            Derived from CI's OWN post-ADR-0078 number: 1896.9 at 3000 samples (run
#                            29848504904, PASS). That single reading carries an unknown 0-3 quanta of +-22 B,
#                            so the 3000-sample floor is somewhere in [1875,1897]; arm64's 3000-floor -> 60000
#                            step is +58 B, ~+61 scaled for x86_64 -> about 1936-1958, call it ~1945 +-25.
#                            The 2040 ceiling is therefore left UNCHANGED: its pass window [1836,2040] clears
#                            that whole range with ~75 B to spare above and ~95 B below, so CI neither
#                            ratchet-demands nor regresses whichever way the estimate is wrong.
#                            ▶️ READ CI's ACTUAL 60000-SAMPLE NUMBER AND TIGHTEN THIS ROW. The same arch
#                            divergence made the FlatData vtable-vs-classic guard flip, and is why one
#                            shared ceiling cannot work.)
