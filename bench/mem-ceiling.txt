# NFR-MEM allocation ratchet (ADR 0062). One ceiling PER ARCHITECTURE, in bytes/sample.
#
# ⚠️ RE-BASELINED 2026-07-21 (workload) AND RAISED 2026-07-21 (ADR 0078 REVERTED). Neither number below is
# comparable to a row from before that date. Two separate things moved them:
#
# 1. THE WORKLOAD. mem-per-sample went from 3000 to 60000 samples because the gate had become BLUNTER THAN
#    THE WINS IT GUARDS: the measured window carries a FIXED ~65 KB per-run allocation occurring 0-3 times,
#    which at 3000 samples landed as a ~22 B/sample quantum — ONE UNCHANGED ARM read 1791 / 1813 / 1835 /
#    1857, a ~65 B spread against a typical slice's ~35 B win. The quantum is per RUN, so it shrinks as
#    1/samples: spread ~65 B at 3000, ~3 B at 30000, ~0.4 B back-to-back at 60000 (~3 B across a session).
#    Changing `samples` is therefore a re-baseline of BOTH rows, never a free knob.
#
# 2. ADR 0078 WAS REVERTED, so its ~-33 B/sample went with it and the ceilings went back UP. The RX
#    store-copy pool caused HEAP CORRUPTION on Linux — proven by isolation on a real Linux box, see the ADR.
#    This is the documented exception to "the ratchet only moves DOWN": a reverted win is not a regression,
#    and pretending otherwise would leave a ceiling no code can meet.
#
# BOTH ROWS ARE MEASURED, at 60000 samples, and x86_64 is for the first time measured DIRECTLY rather than
# predicted from a CI reading or derived from the other arch (a prediction that had been 58 B off):
#   arm64   1878.4-1880.6   (dev box, Apple silicon, SBCL)
#   x86_64  1916.8-1918.9   (Ubuntu 24.04 x86_64, SBCL 2.2.9 — the same OS family and arch as CI)
# Ceilings are set ~30 B above the measured maximum, about 10x the session-scale spread.
#
# The ratchet only moves DOWN, except for the two documented re-baselines above (a workload change or a
# reverted win — and either must say so here). Lower a row when you bank a win on THAT arch.
#
# ⚠️ YOU CAN ONLY LOWER THE ROW FOR THE ARCH YOU MEASURED ON. gate-mem reads the row for `uname -m`, so a
# win banked on the dev box lowers arm64 and leaves x86_64 stale — and the ratchet then FAILS ON
# IMPROVEMENT in CI, which is red until someone reads the CI number and lowers that row too. This is not
# hypothetical: CI was red from the 5th TX slice for exactly this reason. AFTER a win, check the CI
# gate-mem number and lower the OTHER arch's row in the same or an immediate follow-up commit.
#
# LOWERED 2026-07-26 (ADR 0087 — the TX key-hash serialization scratch is CAS-borrowed). BOTH rows were
# measured directly on this slice, and the two arches moved by materially different amounts, which is why
# neither was derived from the other:
#   arm64   1852.2 -> 1769.8   (-82.4)   dev box, Apple silicon, SBCL
#   x86_64  1902.8 -> 1777.4   (-125.4)  Ubuntu 24.04 x86_64, SBCL — same-image A/B (the shipped body
#                                        measured, then %write-key-hash redefined to its pre-0087 body)
# The x86_64 row had also gone stale since 2026-07-21 (wins landed on both arches without it being
# re-measured), so its drop is larger than this slice alone; the A/B above isolates the slice's own share.
#
# LOWERED 2026-07-26 (ADR 0088 — the control-path proxy-key cache). Both rows measured directly again,
# and again the two arches moved by materially different amounts, which is why neither is ever derived
# from the other:
#   arm64   1769.8 -> 1742.1  (-27.7)
#   x86_64  1777.4 -> 1704.5  (-72.9)
# ⚠️ TWO CEILINGS PER ARCH SINCE 2026-07-28 (ADR 0093 slice 1). Format:
#
#     <arch>  <ceiling-COPY>  <ceiling-RETURN>
#
#   COPY   — the legacy workload: the application takes samples and DROPS them. Unchanged, and every
#            historical row above refers to this column, so it stays comparable across the whole campaign.
#   RETURN — the application RETURN-LOANs each taken sample, i.e. honours the ADR 0093 loan contract, so
#            the reader can recycle its delivery wrappers. This is the workload a zero-allocation
#            application actually runs, and the only one in which the recycling can be seen at all.
#
# `-` means NOT YET MEASURED ON THIS ARCH. gate-mem still MEASURES that arm and PRINTS the number (with
# the row to paste in), but does not ratchet it — so an unmeasured arch reports the figure it needs
# instead of going red. ⚠️ NEVER fill a `-` from the other arch's number: the two diverge materially and
# unpredictably (ADR 0087 −82.4 vs −125.4; ADR 0088 −27.7 vs −72.9), and a predicted x86_64 value has
# already been 58 B wrong once. Measure it on that arch, or leave the dash.
#
