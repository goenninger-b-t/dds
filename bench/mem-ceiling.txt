# NFR-MEM allocation ratchet (ADR 0062). One ceiling PER ARCHITECTURE, in bytes/sample.
#
# SBCL's per-sample allocation differs materially by arch — measured, not assumed:
#   arm64   1988-2031      (2026-07-21: + RX-pooling: the %deserialize-sample copy scratch (ADR 0073) and
#                            the drain's %instance-handle key-serialization scratch (ADR 0075, -80 B/call);
#                            floor 2118 -> 1988, cumulative ~-1572 from 3560, ADR 0062/0065-0068/0072/0073/0075)
#   x86_64  2083 B/sample   (2026-07-21, read off CI: + RX-pooling deser-scratch (ADR 0073) + %instance-handle
#                            key-serialization scratch (ADR 0075); floor 2388 -> 2083, still ~5% above arm64. The
#                            same divergence made the FlatData vtable-vs-classic guard flip, and it is
#                            why a single shared ceiling cannot work: at the x86_64 number the arm64
#                            ratchet would never bite, and at the arm64 number x86_64 is permanently red.)
#
# The ratchet only moves DOWN. Lower a row when you bank a win on THAT arch (gate-mem tells you).
#
# ⚠️ YOU CAN ONLY LOWER THE ROW FOR THE ARCH YOU MEASURED ON. gate-mem reads the row for `uname -m`, so a
# win banked on the dev box lowers arm64 and leaves x86_64 stale — and the ratchet then FAILS ON
# IMPROVEMENT in CI, which is red until someone reads the CI number and lowers that row too. This is not
# hypothetical: CI was red from the 5th TX slice for exactly this reason. AFTER a win, check the CI
# gate-mem number and lower the OTHER arch's row in the same or an immediate follow-up commit.
