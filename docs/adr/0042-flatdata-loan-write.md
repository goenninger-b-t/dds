# ADR 0042 — FlatData loan-write: an app-facing zero-copy TX API that writes the sample directly into the SHMEM pool slot

- **Status:** Accepted (WP-FLATDATA-LOAN-WRITE, 2026-07-03) — **NOT cleared for ship, pending counsel (R6)** (the whole Zero-Copy/FlatData feature area carries the patent-review marker; ADR 0014/0015/0017).
- **Deciders:** A0 (integrator), A10 (perf/features)
- **Requires:** REQUIREMENTS FR-PF-4 (FlatData), FR-PF-3 (Zero-Copy/SHMEM), NFR-MEM (static/zero steady-state allocation), NFR-CLOS (hot-path purity), NFR-SEC-POSTURE (bounds-checking); the operating contract §4 (never hardcode a wire constant; bounds-check network-facing buffers), §6 (no perf change without a before/after measurement).
- **Amends / builds on:** ADR 0014 (WP-ZEROCOPY pool), ADR 0015 (WP-FLATDATA-over-ZC), ADR 0017 (WP-FLATDATA-ZC-LOAN read-in-place RX), ADR 0018 (WP-ZC-LOAN-LOCKFREE). Additive: it splits `%zc-loan` into composable primitives (`%zc-loan` stays a byte-behaviour-identical composition) and widens the generated FlatData Offset setter to a SAP-mode branch — no consumer of an existing symbol changes.
- **Resolves:** ADR 0015 deferred follow-up #4 ("loan-write API"), ADR 0014 follow-up ("get-loan/return-loan write API"), ADR 0017 §"write-side dual", **ADR 0036 Carry-10** forward requirement (the loan-write TX site inherits the SHMEM-cleartext security gate).

---

## Context

TX of a FlatData sample to a same-host Zero-Copy reader costs **two intra-host copies** today, on top of the app's own field writes:

1. `write-sample` → `%serialize-sample` runs the FlatData identity serializer `serialize-<name>-fd` (`src/dds-gen/dsl.lisp`), block-copying the app's foreign FlatData buffer body into a freshly-allocated heap SerializedPayload vector.
2. At send time the single ZC chokepoint `%zc-change-item` → `%zc-ref-builder` → `%zc-loan` (`src/dds-xport/zerocopy-pool.lisp`) copies that payload into the writer pool slot (the `dotimes` copy loop), then publishes a 16-byte reference.

ADR 0015/0017 named the remaining app→slot copy "the documented v1 limitation; a loan-write API that writes the sample straight into the slot is the explicit follow-up." This ADR is that follow-up. The RX-side literal-0-copy loan already exists (`%zc-acquire-for-read` / `%zc-release`, ADR 0017/0018); loan-write is its **write-side dual**: the app acquires a pool slot, writes its FlatData fields **directly into the slot** through the SAP-mode Offset accessors, and commits — eliminating both copies for the eligible configuration.

## Decision

### 1. Split the loan into three composable pool primitives (`dds.xport.zerocopy`)

`%zc-loan` is refactored into an **acquire / commit / abort** state machine; `%zc-loan` itself becomes the thin composition `acquire → copy → commit`, so every existing caller and bench is behaviour-identical (same return values, same slot contents, same generation sequence — the mutex hold *duration* shrinks, which is not observable behaviour).

- `%zc-loan-acquire (sap len readers) → (values slot payload-base generation)` — the slot bookkeeping **without** the copy: reject `len > slot-bytes`; take the pool mutex; `%zc-take-free-or-reclaim` (lowest-pubseq `refcount==0` slot); set `len`, `refcount=readers`, `pubseq`; compute the next generation `g = (old+1) & #xFFFFFFFF` **but do not store it**; release the mutex. Returns the slot index, the segment-relative payload base (`slot-off + slot-hdr`) the writer writes into, and `g` for the later commit. `(values nil 0 0)` on oversize / saturation.
- `%zc-loan-commit (sap slot generation)` — the publication tail: `dds.pal:fence :release` then store the slot generation `= generation` **last**. This is the single release point that publishes the fully-written slot to a future lock-free reader.
- `%zc-loan-abort (sap slot)` — release the writer's hold: take the mutex, set `refcount = 0`; the generation is **never** stored, so no new generation is ever published. The slot becomes reclaimable (`refcount==0`) exactly as if it had never been loaned.

### 2. The acquire/commit/abort vs lock-free-reader ordering argument (the correctness crux)

The invariant that makes loan-write safe is **identical** to `%zc-loan`'s: *the new generation `g` is stored only at commit, after the app's writes and a release fence.* Trace every interleaving against the reader's `%zc-acquire-for-read` (load generation → `fence :acquire` → compare against the expected `g` from its ref → dependent len/payload reads):

- **A reader can never observe a slot mid-app-write.** Between acquire and commit the slot's stored generation is still the *old* value; the ref carrying the new `g` is emitted only after commit (at send time), so no reader is even holding `g` yet — and even a hypothetical stale ref bearing `g` fails the generation compare because `g` is not stored until commit. Only after commit's `fence :release` + generation-store does a reader that acquire-loads `g` see the app's writes (the release/acquire pair forbids a torn read). This is byte-for-byte the `%zc-loan` handshake (ADR 0018), with the app's field writes substituted for the copy loop between the acquire bookkeeping and the commit store.
- **The slot cannot be stolen or force-reclaimed during the app write.** `acquire` set `refcount = readers ≥ 1` under the mutex; `%zc-take-free-or-reclaim` only ever selects `refcount==0` slots, so no other writer can reclaim or re-generation this slot while the app holds it. The slot's generation/len are therefore stable between acquire and commit — commit's store of `g` cannot race another writer.
- **Commit needs no mutex.** Once `refcount>0` is set, only this writer touches the slot; the store's cross-process *visibility* comes from the `fence :release` + generation-store (the release half of the handshake), not from the mutex — exactly as the reader's `%zc-release` does its refcount CAS without the mutex (ADR 0018). Keeping commit lock-free is what lets the app write outside any lock.
- **An aborted loan leaves the slot reclaimable and never publishes a generation.** `abort` restores `refcount=0` (under the mutex, so it cannot tear a concurrent `%zc-take-free-or-reclaim` refcount read) and leaves the generation at its old value. Since no ref bearing the would-be `g` was ever emitted (refs are emitted only at commit → send), no reader can ever present that `g`; a future loan on the slot recomputes `old+1` and stores it only on *its* commit. So abort is invisible to every reader — pure best-effort discard.

### 3. Widen the generated FlatData Offset setter to a SAP-mode branch (`dds.gen`)

The generated `<name>-<field>-fd` **getter** already dual-dispatches (owned `octet-buffer` → `aref` vec read; `flatdata-view` → SAP read). The **setter** was owned-buffer-only. It is widened symmetrically: a new macro-time `%flatdata-sap-setter-form` emits per-byte `dds.pal:store-sap-u8` writes (LE, byte-exact to the `aref` form, matching the SAP getter's per-byte `load-sap-u8` compose — never native-order `store-sap-u16/u32`, so byte-exactness is guaranteed), and the setter branches `flatdata-view` → SAP write, `octet-buffer` → the unchanged `aref` write. The owned-buffer path is untouched → byte-identical. A `flatdata-view` is therefore now **read-write** (the RX view stays read-only by usage; the writer-loan view is the write user). No wire constant is introduced — the encapsulation header for a slot-backed loan is sourced from the type's existing FlatData constructor (§4), never hardcoded.

### 4. App-facing DCPS loan-write API (`dds.dcps`), the writer-side dual of the reader loans

- `loan-sample (dw)` → a writer-side loaned FlatData sample the app fills via the existing `<name>-<field>-fd` setters (a `writer-loan` `defstruct`, **no CLOS**; the struct + `flatdata-view` recycle through a per-writer freelist — but each `loan-sample` conses one registry cell and each `write-loaned` allocates the retained payload + one armed-registry cell, the **documented v1 allocations**; this is control-plane DCPS code, NOT covered by the `gate-hotpath` scan set). When the **full ZC-TX eligibility** holds — pool exists, FlatData type, `+<name>-flatdata-size+ > *zerocopy-min-payload-bytes*`, `(not (%zc-payload-wire-protected-p node))`, `(not (%loan-write-data-protected-p node))` (§6) — the loan is **slot-backed**: `%zc-loan-acquire` a slot (`readers=1`), write the 4-octet encap header in place (copied once, off the steady-state field-write path, from the per-type constant the FlatData constructor produces), and hand the app a `flatdata-view` over the slot body — the slot is therefore a **self-describing SerializedPayload** (bytes `[base, base+4)` byte-identical to what `%zc-loan` copies in on the classic path; asserted by `dcps-loan-write-e2e`). Otherwise the loan **degrades gracefully** to a heap/pool-backed FlatData sample (the existing `make-<name>-flatdata` constructor) — same API, no error, no downstream behaviour change.
- `write-loaned (dw loan)` → publishes the loaned sample. Fallback-backed: exactly `write-sample`. Slot-backed: materialise the RETAINED payload (one slot→heap copy — §5), `%zc-loan-commit` the slot, then publish with the change **carrying the pre-committed slot** so the send site emits its ref without any copy (§5).
- `discard-loan (dw loan)` → abandon without publishing (slot-backed: `%zc-loan-abort`), idempotent (a double-discard / a write-after-discard is a validated no-op), plus a writer-close safety sweep mirroring `return-all-loans`.

### 5. Send-site integration, the correctness envelope, and the slot lifecycle (as shipped)

Loan-write is an **optimization of the existing ZC TX path**; every case the current path handles must still work identically. The published change's history payload is what feeds retransmission (`%data-builder`/`%sample-plan`), non-ZC destinations, and per-destination ZC re-loan (`%zc-ref-builder`, `resolves=1`). `write-loaned` therefore **retains a serialized payload** (one slot→heap copy, matching today's `%serialize-sample` cost) **and** hands the pre-committed slot to the send site so the ZC leg emits the ref **without any copy**:

**The change carries the committed slot identity.** `cache-change` gains three inert-by-default slots — `zc-slot` (fixnum, −1 = none), `zc-generation` (u32), `zc-state` — set at construction under the writer lock (`writer-write` optionals; the change is *born* `:armed`, so a concurrent capture can never observe a half-armed change). No per-sample allocation is added to the send path (fixnum/symbol struct slots; the armed-registry cons happens at `write-loaned`, which already allocates the retained payload).

**Lifecycle state machine** (transitions one-shot, under the owning writer's lock — `writer-zc-claim` / `writer-zc-unarm`; the same lock discipline as `send-refcount`):

```
NIL ──(writer-write zc-slot)──► :ARMED ──claim (send site, ZC-eligible dest)─► :CONSUMED (refcount → the reader)
                                  │
                                  └──unarm (fallback decision / sweep) + %zc-release──► :RELEASED (refcount → 0)
```

- `:armed → :consumed` — `%zc-change-item` (the single ZC send chokepoint, reached by BOTH push entry points: `%push-data-buf` sync/async and `%node-datagram-plan` flow-paced, via `%changes-datagram-plan`) prefers the pre-committed slot when the **full** eligibility holds (`zc-readers > 0`, kind `:data`, security gate clear, len > min): `%zc-armed-item` claims one-shot and emits `%zc-ref-item` on the **pre-committed** (slot, gen) — **no payload→slot copy**; the ref bytes are byte-identical to a fresh `%zc-ref-builder` emission (`%encode-zc-ref-vec` + `write-data`, the same emitters — proven byte-equal in `loan-write-sendsite`). The slot's `refcount=1` now belongs to the **resolving reader** (released at resolve / `return-loan`). The claim is spent on the **first** ZC-eligible destination.
- `:armed → :released` — every send-time fallback decision releases the slot (`%zc-drop-armed`: unarm + `%zc-release`, refcount 1→0, reclaimable; the committed generation stays in place — a later loan bumps it, invalidating any stale ref): the **security gate** (`%zc-payload-wire-protected-p` — the send-site gate stays authoritative over the pre-committed slot, ADR 0036 Carry-10), a **non-ZC destination** (`zc-readers = 0` — which includes **every retransmit**, since the ACKNACK repair path passes no `zc-readers`), a non-`:data` kind, or an undersized change.
- **Leak-safety sweeps** (a committed slot must never strand at `refcount ≥ 1`, since reclaim only takes `refcount == 0`): (a) the **push-pass sweep** — both push entry points snapshot the node's armed-change registry (`disc-node-zc-armed-changes`, populated by `publish-sample` and guarded by the node lock) before the pass and `%zc-armed-sweep` exactly that snapshot after it (changes armed concurrently by a mid-pass publish are prepended ahead of the snapshot and survive to their own pass — never released before they were ever presented), releasing any change the pass never presented (zero destinations, debug-drop, KEEP_LAST-evicted before its push); (b) the **`stop-node` teardown sweep** (before the pool is destroyed); (c) `publish-sample` releases the slot itself on `:timeout` (nothing added → never emittable) — proven by the bounded-cache fixture `run-loan-write-timeout-release-test` (WP-RESIDUAL-FIXES-BATCH-A: KEEP_ALL `max_samples 1` + `max_blocking_ns 0`, a second publish carrying a committed slot returns `:timeout`, the pool free-count is restored and the armed registry stays empty). A `discard-loan` before publish uses `%zc-loan-abort` (uncommitted — no generation ever published).
- **Retransmit-after-consume never double-emits the slot**: the refcount covers exactly one resolve; a consumed change's repair leg takes the retained payload (`zc-readers=0 → NIL → %data-builder`), and even a hypothetical ZC re-emit takes a **fresh** loan (the claim is lost). Proven by `loan-write-sendsite`.

**The envelope.** The **pure end-to-end zero-copy TX** — the delivered bytes are the app's SAP-setter writes, with no app→slot copy and no slot→heap copy anywhere on the delivering leg — applies when the change resolves to **exactly one ZC destination** at send time (the ADR-0017 one-loan-capable-reader invariant; `resolves=1`) with the gates clear. Proven end-to-end by `dcps-loan-write-e2e`: the reader's `take-loaned` view carries **exactly the loan's (slot-index, generation)**, `zc-sends = 1`, and the pool never loses a second slot. Every other case — 0 or > 1 ZC destinations, retransmission, non-ZC readers, gate active — is served from the retained payload **exactly as today** (a further ZC destination pays a fresh `%zc-loan`, as `write-sample` does; a discovery flip degrades to the fallback, never corruption). Correctness is never narrower than the shipped path; only the *optimization* is. We do **not** widen slot lifetime into retransmit territory (a slot pinned until acked) — explicitly out of scope v1; see Follow-ups.

### 6. Security gate inheritance (ADR 0036 Carry-10 — acceptance criterion)

The loan-write TX site inherits the security gates **fail-closed at both ends**: (a) `loan-sample` on a wire-protected node (rtps_protection or user-submessage/metadata protection ≠ `:none`) returns the **non-slot fallback** sample — a secured writer's plaintext never lands in a pool slot at all; (b) the send-site gate at `%zc-change-item` stays authoritative for whatever reaches it — a pre-committed slot on a gated change is **ignored and released** (`loan-write-sendsite` proves the veto + release). **ADR 0036 Carry-10 is resolved here.** Additionally — and unlike the classic ZC path, where `data_protection` is intentionally un-gated because the pool receives the already-transformed SecuredPayload — **loan-write MUST also gate `data_protection`** (`%loan-write-data-protected-p`): the slot holds the app's *pre-transform* field writes, so a transformed payload would make the slot BOTH a plaintext leak into SHMEM and a format mismatch against the wire. The gate mirrors `publish-sample`'s exact transform condition, fail-closed: governance `:sign`/`:encrypt` always blocks; `:unset` blocks iff a crypto-transform is installed (the Slice-1 direct-KM config); governance `:none` rides plain. `publish-sample` carries a redundant fail-safe (releases a slot handed in under a transforming config).

## Consequences

- **Positive:** both intra-host TX copies are eliminated on the ZC leg — the app writes fields straight into the slot (SAP setters) and the send site emits the pre-committed slot's ref with no copy (`loan-write-sendsite` bench arm: the 8 KiB payload→slot copy gone, ~29x faster ref emission; `dcps-loan-write-e2e` proves the delivered view references the app-written slot). The pool primitive split is reused (DRY): `%zc-loan` is now `acquire+copy+commit`, and `%zc-ref-builder`/`%zc-armed-item` share `%zc-ref-item`.
- **Cost / honest framing (FR-LANG-7):** the claims are scoped precisely — the **send-site payload→slot copy is eliminated** (the 0-copy claim; ~29x at 8 KiB in the send-site bench arm) and the **pool primitives are 0-GC**; **v1 `write-loaned` itself is NOT 0-GC**: it materialises ONE retained payload (slot→heap, matching today's `%serialize-sample` cost — it lives in the writer HistoryCache to serve retransmission / non-ZC / extra-ZC destinations, so it cannot be pooled/reused without corrupting history) plus two registry list cells per write (the loan registry + the armed registry). The DCPS-cycle bench arm prices the real `loan-sample`→`write-loaned` cycle honestly: on an UNMATCHED writer with a tiny 20-octet sample it is *slower* than `write-sample` (the fixed slot acquire/commit + retained-copy + sweep overhead with no ZC destination to pay it back); the win requires a same-host ZC reader and scales with payload size. All eliminated only by the acked-slot-pinning follow-up. The state transitions add one brief writer-lock acquisition per armed change per destination decision (plain changes pay a single fixnum-slot read).
- **Wire:** byte-identical for every existing path; a loan-written change emits exactly the `%encode-zc-ref-vec` ref bytes on the ZC leg (proven byte-equal) and the exact `write-sample` DATA elsewhere. Corpora/KATs untouched.

## Follow-ups

- **Reliable / acked slot pinning (retained-payload elimination):** keep a slot loaned until every reliable reader has acked, so a reliable writer needs no retained payload at all (the HistoryCache change would own the slot lifetime and release it on the ACKNACK purge). Out of scope v1 — the retained payload keeps repair byte-exact today.
- **Multi-ZC-destination refcounting:** commit a slot with `readers = ZC-destination-count` and emit one ref per ZC destination, so N same-host ZC destinations share one slot with no re-loan. v1 spends the claim on the first ZC destination and re-loans for the rest (exactly today's cost for them).
- **Encap-header caching:** the per-type 4-octet encap header is materialized once from the FlatData constructor and cached on the type-support; revisit if a future non-FINAL FlatData type makes it non-constant.
